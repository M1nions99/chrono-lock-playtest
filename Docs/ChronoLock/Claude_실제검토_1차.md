# 코드 리뷰 (2차) — ChronoLock 프로토타입

7개 항목으로 정리했습니다. 각 항목은 "문제 → 최소 수정안" 형식입니다.

**1. (블로커) 게임 로직과 플레이어 이동의 실행 순서가 보장되지 않음**
`ChronoGame.Update()`와 `ChronoPlayer.Update()`는 서로 다른 컴포넌트라 Unity 기본 실행 순서가 불명확합니다. 게임 로직이 플레이어 이동/시점 회전보다 먼저 도는 프레임이 있으면 조준 레이캐스트·체크포인트·위험구역 판정이 한 프레임 지연됩니다.
→ Script Execution Order에서 `ChronoPlayer`를 `ChronoGame`보다 앞에 두거나, 게임 틱 로직을 `ChronoPlayer.Update()` 끝에서 직접 호출하도록 합치세요.

**2. (블로커) 다리(Bridge) 상태가 되감기로만 바뀌고, 완전히 소진된 뒤 피드백이 없음**
`TemporalDevice.Tick`의 정방향(가속/보통) 분기에는 Bridge 케이스가 없어(`if (kind != DeviceKind.Bridge)`), 되감기로 복구를 다 끝낸 뒤 다시 가속/정상으로 바꿔도 아무 일도 일어나지 않습니다. 또한 history가 1개 남으면 이후 되감기 클릭이 조용히 무시되어 플레이어는 "고장났다"고 오해할 수 있습니다.
→ `HistoryCount==1`일 때 "복구 완료, 더 되감을 기록 없음" 같은 별도 안내 메시지 추가.

**3. (블로커 후보 / 밸런스) 회전 구간 내 장치 전환이 즉시 사망으로 이어짐**
위험구역(z 8.7~11.5) 안에서 다른 장치를 좌클릭하면 `Release()`가 즉시 rotor를 Normal로 풀어버려 다음 프레임에 강제 리커버됩니다. 의도된 긴장감인지, 실수 방지가 필요한지 확인 필요.
→ 의도가 아니라면 위험구역 체류 중엔 다른 장치로 타겟 전환/적용을 막는 가드 추가.

**4. (1인칭 체감) 마우스 감도가 프레임레이트에 종속, 착지/이동 피드백 전무**
`m.delta`는 `deltaTime` 보정이 없는 원시 델타라 프레임레이트마다 회전 속도가 달라집니다. 점프/착지/스프린트 시 헤드밥·FOV 킥·랜딩 임팩트가 전혀 없어 "절차 사운드/손목 장치" 폴리시 이전에도 체감이 밋밋합니다.
→ 최소한 착지 시 카메라 y 오프셋 감쇠(코루틴)와 스프린트 FOV 보간만 먼저 추가 권장.

**5. (아트 교체 리스크) `ApplyVisual()`이 placeholder 프리미티브 기준 하드코딩**
스케일(`.1f+state*2.5f`), 회전(`Euler(0,0,state)`), 절대 월드 좌표(`localPosition z=35`) 등이 지금 박스형 레벨 좌표에 맞춰져 있습니다. 리액터/콘솔/다리 메시를 실제로 모델링하면 피벗 불일치·클리핑이 발생하고, 레벨을 세라믹 패널로 재구성하면 좌표도 다시 손대야 합니다.
→ state(0~1)를 Animator 커브나 로컬 앵커 기준 상대 오프셋으로 매핑해 아트팀이 스크립트 수정 없이 재배치 가능하게 분리.

**6. (테스트 가능성) 게임 로직이 Keyboard/Mouse와 OnGUI에 강결합**
`HandleInput`은 실제 `Keyboard`/`Mouse` 인스턴스 없이는 호출 불가, `target`은 private이라 Play Mode 테스트에서 상태를 직접 검증할 방법이 없습니다.
→ `TrySelectMode(mode)`, `TryApplyToTarget()`, `TrySecure()` 같은 순수 public 메서드로 입력 로직을 분리하고 `CurrentTarget`을 읽기 전용으로 노출하면, InputTestFixture 없이도 "회전구간 통과 → 리액터 충전 → 다리 복구 → 탈출" 플로우 테스트 작성 가능.

**7. (렌더링 전환 이슈) HUD가 전부 OnGUI(IMGUI)로 구현됨**
요구사항의 "컴팩트 한국어 HUD" + 3D 손목 시간장치를 같이 넣으려면 문제가 됩니다. OnGUI는 항상 카메라 렌더 위 최상단에 그려지므로 손목 장치(월드/카메라 공간 오브젝트)와 레이어링이 충돌하고 안전영역/해상도 대응도 취약합니다.
→ HUD를 UI Toolkit(UGUI)로 이전하고, 손목 장치는 별도 오버레이 카메라/레이어로 분리해 폴리시 단계에서 재작업 범위를 줄이세요.

---
추가로, 요청하신 "실제 Play Mode 플로우 테스트"는 5번·6번 수정(순수 메서드 분리)이 선행되어야 안정적으로 작성 가능합니다. 디바이스 유닛 테스트만으로는 회전→리액터→다리→탈출의 통합 시퀀스를 검증하지 못합니다.
